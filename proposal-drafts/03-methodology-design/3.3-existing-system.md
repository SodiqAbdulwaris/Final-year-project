## 3.3 Analysis of the Existing System

### 3.3.1 Description of the Existing System

In the baseline arrangement, a client application calls one predetermined LLM deployment for every request. The project will reproduce this arrangement as a fixed-model reference for comparison. It is not presented as a survey finding about how all developers work. Existing gateways already support routing and recovery in several forms (LiteLLM, n.d.; OpenRouter, n.d.; Portkey, n.d.; Section 2.5), so the comparison also includes current gateway practice.

Research comparators include pre-generation routing and cascades. Hybrid LLM uses quality-aware routing, RouteLLM learns from preference data, and FrugalGPT escalates according to the response (Ding et al., 2024; Ong et al., 2025; L. Chen et al., 2024). The study does not assume that any of these features is absent from earlier work.

### 3.3.2 Limitations of the Existing System

The following are design risks and comparison boundaries to be investigated, not claims that every existing product has them.

- Fixed model. There is no request-specific choice of model. Alternatives will be compared on measured quality, cost and latency.
- Quality-only selection. A high predicted score may point to an unaffordable or unavailable deployment. Hard filters and feasibility constraints will be applied first.
- Complex hybrid. Extra feature extraction may erase inference savings. Overhead and component ablations will be measured.
- Offline replay. Stored outcomes do not reproduce present network or failure behaviour. Replay will be kept separate from a capped live pilot and fault injection.
- Generic retry. Repeating a call may spend budget again or repeat side effects. Recovery will be bounded, will respect eligibility and will count every attempt.
