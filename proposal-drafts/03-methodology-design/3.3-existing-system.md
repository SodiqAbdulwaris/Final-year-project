## 3.3 Analysis of the Existing System

### 3.3.1 Description

The baseline scenario will consist of a client that will call one predetermined LLM deployment for every request. It will be reproduced as a fixed-model reference, not presented as a survey finding about all developers. The comparison will also include existing gateway practice, which already supports routing and recovery in various forms (vendor documentation, accessed 31 October 2026; Section 2.5).

Research comparators will include pre-generation routing and cascades. Hybrid LLM uses quality-aware routing, RouteLLM uses preference data, and FrugalGPT uses response-dependent escalation (Ding et al., 2024; Ong et al., 2025; L. Chen et al., 2024). The study will not assume that a gateway feature or a learned router is absent from prior work.

### 3.3.2 Limitations

| Comparison scenario | Limitation to investigate | Proposed response |
|---|---|---|
| Fixed-model baseline | No request-specific model choice. | Compare alternatives at measured quality, cost and latency. |
| Quality-only selection | A high score may still identify an unaffordable or unavailable deployment. | Apply hard filters and feasibility constraints. |
| Complex hybrid | Extra feature extraction may erase inference savings. | Measure overhead and component ablations. |
| Offline replay | Stored outcomes will not reproduce present network or failure behaviour. | Separate replay from a capped live and fault-injection evaluation. |
| Generic retry | Repeating a call may consume budget or repeat side effects. | Bounded, eligibility-preserving operational recovery and attempt accounting. |

These will be design risks and comparison boundaries, not universal claims that every existing product has these limitations.
