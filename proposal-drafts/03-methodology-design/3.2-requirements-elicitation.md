## 3.2 Requirements Elicitation

Requirements will be derived primarily from the governing design, the motivating fixed-model scenario, literature and documented gateway behaviours. The team will walk through normal requests, unaffordable requests, missing capabilities, provider throttling, timeouts and partial delivery. Each scenario will yield an observable requirement and an acceptance-test entry.

| Source | Elicitation activity | Output |
|---|---|---|
| Governing design and owner decisions | Resolve core, optional and unresolved scope. | Requirement source IDs and MoSCoW priorities. |
| Benchmark schemas | Inspect model/task coverage, quality labels and usage fields. | Data and reproducibility requirements. |
| Operational scenarios | Walk through failures, concurrent requests and budget exhaustion. | Retry, accounting, security and monitoring requirements. |
| Team review | Review the proposed API and dashboard wireframes. | Recorded design feedback, not a population usability result. |

No mandatory interview or System Usability Scale sample will be carried over from the old guide. Human involvement will be minimal or absent. If an optional participant exercise is later selected, informed consent, anonymous responses and a documented instrument will precede collection. Appendix C will then be extended; this proposal will not imply that interviews or surveys have already occurred.
