## 3.4 The Proposed System

### 3.4.1 Description

The proposed system will provide a common request gateway over a registered pool of hosted and local model deployments. It will validate the request, filter mandatory constraints, analyse task/capability features, retrieve permitted historical evidence, predict per-model suitability and select the cheapest feasible candidate. Execution will occur through adapters, with a separate controller for health state, circuit breakers, bounded attempts and outcome accounting.

A model will describe capability and version; a deployment will identify a runnable endpoint and its current health, price profile and latency history. This separation will allow the evaluation to distinguish model quality from deployment conditions. Monitoring will record selection reasons, exclusions, predicted values and observed outcomes without routinely retaining raw prompts.

### 3.4.2 Justification

| Design choice | Justification | Objective |
|---|---|---|
| Deterministic filtering before selection | Hard restrictions will not be traded away for predicted quality. | O1, O3 |
| Lightweight classification and optional retrieval features | Components will be independently testable and practical for limited compute. | O2 |
| Constrained cheapest-feasible selection | Cost optimisation will operate within declared quality and deadline constraints. | O3 |
| Separate reliability controller | Execution failures will be distinguished from inadequate completed answers. | O4 |
| Common adapters and versioned logs | Baselines and hybrid will share execution and measurement conventions. | O4, O5 |
| Replay plus a capped live subset | Scored-output reuse will save API cost while live tests will measure operational behaviour. | O5 |

The architecture will initially be modular within one application. This will be a provisional engineering choice, not a claim that Redis/Prometheus or other unresolved earlier proposals have been permanently rejected.
