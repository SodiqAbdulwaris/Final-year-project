### 3.6.5 Algorithm and Model Design

For a request q and a candidate model m, the predictor will estimate suitability as a function of task, difficulty, similarity and model:

```text
Q̂(m, q) = f(task, difficulty, similarity, model)
```

Classification is lightweight. Mandatory request fields are filtered first, and any capability requirement found during analysis is applied again before selection. The classifier never weakens an explicit client restriction. Difficulty and similarity are predictive features and not independent proof of quality, and similarity features come only from permitted historical outcomes. A score will not be called a probability unless its label definition and calibration justify that.

Let E(q) be the deployments that pass capability, context, privacy, health and preliminary affordability rules, B_rem the remaining permitted budget, D_rem the remaining deadline and τ the minimum predicted quality. The feasible set is:

```text
F(q) = { m ∈ E(q) : Q̂(m, q) ≥ τ,  Ĉ(m, q) ≤ B_rem,  L̂(m, q) ≤ D_rem }
```

The selected deployment minimises expected cost among the feasible candidates:

```text
m* = argmin over m ∈ F(q) of Ĉ(m, q)
```

Predicted latency breaks ties, followed by a stable deployment identifier so that runs can be reproduced. Predicted feasibility does not guarantee observed quality or latency, so those violations are measured. Before execution, a conservative reservation based on input and output caps supplements the expected-cost ranking. If chargeable tokens cannot be bounded, a hard budget requires a conservative bound or rejection.

A weighted utility will be evaluated only as a comparator:

```text
U(m, q) = α·Q̂(m, q) − β·C̃(m, q) − γ·L̃(m, q)
```

The tildes mean normalised cost and latency; scaling constants and weights are chosen on validation data only. The comparator still obeys the hard restrictions, because cheap inference cannot make up for an unsupported capability or unauthorised spend. The routing procedure is:

```text
ROUTE(q, policy):
  validate client, payload, authorised endpoints and declared constraints
  initialise finite attempt allowance, deadline and request accounting
  while allowance remains and caller has not cancelled:
    E <- filter capability, context, privacy, health and budget rules
    features <- classify q; retrieve only permitted historical evidence
    E <- re-apply capability filters using the analysed requirements
    estimates <- predict quality, cost and latency for E
    F <- enforce quality floor, cost cap and remaining deadline
    if F is empty: return explicit INFEASIBLE under the declared policy
    candidate <- cheapest feasible candidate (deterministic tie break)
    atomically revalidate and reserve conservative attempt spend
    if reservation fails: return explicit budget or state error
    consume one attempt allowance
    outcome <- execute with remaining timeout through the adapter
    reconcile known usage; keep reservation for unresolved charges
    record redacted estimates, timing, exclusions and health outcome
    if completed: return response
    if not retryable, unsafe to repeat or partial output sent: return error
  return explicit EXHAUSTED or CANCELLED outcome
```

When no candidate is feasible, the first version will reject the request with an explicit error. Relaxing an explicitly soft preference, or asking the caller for permission to exceed a constraint, are possible later options. No path silently relaxes a hard budget, capability or privacy rule. Retry eligibility, attempt count, cooldown and circuit-breaker thresholds will be set after the pilot. After delivery has begun, the gateway reports failure instead of joining another model’s stream to the first, and calls with unsafe or uncertain side effects are not repeated automatically.

Monitoring feeds an offline calibration process; logging alone is not described as online adaptation. Quality-based cascading remains a separate optional experiment after completed responses, and its verifier calls, cost and latency are counted separately.
