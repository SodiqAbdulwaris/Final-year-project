## 1.11 Definition of Operational Terms

| Term | Meaning in this project |
|---|---|
| Availability | Whether a deployment will currently be permitted to receive a request under health and circuit-breaker policy. |
| Calibration | Agreement between predicted quality or success and observed outcomes for comparable held-out requests. |
| Circuit breaker | A controller that will temporarily block calls after qualifying failures and permit bounded recovery probes. |
| Constrained selection | Choosing a candidate only after its mandatory constraints and predicted feasibility have been assessed. |
| Embedding | A vector representation that will support similarity comparisons between requests. |
| Hard constraint | A requirement that the selector and fallback controller will not silently relax. |
| Latency | A measured duration, reported separately as router overhead, time to first token and end-to-end completion time. |
| Model suitability | The predictor's estimated quality for a particular request and candidate model. |
| Non-inferiority margin | The maximum quality loss the team will justify and predeclare relative to the chosen single-model reference. |
| Operational fallback | A new eligible execution attempt following a qualifying execution failure. |
| p95 latency | The latency value at or below which the stated empirical proportion of observations will fall, using a declared quantile calculation. |
| Quality cascade | An optional escalation after a completed answer is judged inadequate. |
| Retrieval evidence | Historical scored requests that the feature pipeline will be permitted to use without access to evaluated outcomes. |
| Soft preference | A preference that an explicitly documented policy may relax without changing a hard restriction. |
| Utility comparator | A normalised weighted quality–cost–latency score that will be evaluated as a variant, not the default constrained policy. |
