## 1.1 Background

Large language models (LLMs) will be treated in this project as interchangeable candidates for a software service, subject to important differences in capability, price and response time. An application programming interface (API) will separate the client application from each candidate deployment. The routing layer will decide which eligible deployment should process an incoming request, rather than requiring the client to implement a different decision policy for every provider.

Published research offers several ways to make that decision. Hybrid LLM considers quality-aware selection before generation (Ding et al., 2024), while RouteLLM learns routing decisions from preference data (Ong et al., 2025). RouterDC learns relationships between queries and model representations using contrastive objectives (S. Chen et al., 2024). FrugalGPT instead investigates cascades in which acceptance of an earlier response determines whether another model will be called (L. Chen et al., 2024). These approaches will inform the design without being combined wholesale or treated as equivalent algorithms.

The proposed router will distinguish generic prompt difficulty from model-specific suitability. A coding request might be difficult in general yet well suited to a specialised candidate. Lightweight classification will identify task characteristics and capability requirements. Embedding-based retrieval will provide features from similar historical requests with scored per-model outcomes. A predictor will then estimate suitability for each candidate. Whether retrieval improves that predictor will be tested through ablation rather than assumed.

The decision will also have operational constraints. A model that lacks the required context window or output format will be ineligible even if its predicted quality is high. A healthy model may still be too expensive for the remaining request budget, or its predicted completion time may exceed the deadline. These restrictions will be handled explicitly before dispatch. The cheapest candidate meeting the declared constraints will be preferred, subject to the final policy specified in Chapter 3.

The project will separate quality prediction from execution reliability. A timeout or connection failure will trigger operational recovery rules, whereas a completed but inadequate answer could trigger an optional quality cascade. Treating both events as one fallback mechanism would obscure their different costs and causes. Reliability evaluation will therefore use controlled fault injection, while algorithm evaluation will use held-out scored tasks.

The setting will be a resource-constrained undergraduate software-engineering project at Nile University of Nigeria. Two machines with RTX 4070 graphics processing units (GPUs), one desktop and one laptop, will support local development, feature extraction and small-model experiments. Already-scored benchmark outputs will reduce the need for paid calls. Hardware identity will not be taken as evidence that both machines have equal memory, throughput or model capacity; these properties will be measured before live experiments.
