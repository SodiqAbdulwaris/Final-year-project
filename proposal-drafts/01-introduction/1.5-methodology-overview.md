## 1.5 Methodology Overview

The work will follow an iterative artefact-development and controlled-evaluation process. Requirements will first be extracted from the governing design, application scenarios and reviewed evidence. A minimal gateway will provide validation, a model registry and adapters. Fixed-model, cheapest-eligible and rule-based policies will establish the initial comparisons before learned components are added.

Already-scored RouterBench and LLMRouterBench outputs will be considered for offline predictor development and replay evaluation (Hu et al., 2024; H. Li et al., 2026). Their versions, model coverage, task overlap and licence conditions will be checked before data use. Request groups will be separated across training, validation and testing, and evaluated outcomes will be excluded from the retrieval index used to route those requests. The exact split and estimator will remain TODO until the protocol is frozen.

The hybrid will combine classification and retrieval-derived features for suitability prediction. Deterministic eligibility filtering will precede selection. A constrained policy will prefer the cheapest feasible model; a normalised weighted score will be considered only as a comparator. Ablations will isolate the value of classification and embeddings.

A capped live pilot will measure actual latency and gateway overhead because replayed outputs will not reproduce current provider scheduling, network delays or failures. Local deployments will support failure injection at low API cost. Results will include quality, cost, latency, calibration, constraint violations and fallback completion, with paired uncertainty intervals where the sample permits. All tuning decisions will precede the held-out test analysis.
