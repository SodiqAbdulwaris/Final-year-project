### 2.4.5 Latency and load balancing

The review will distinguish model selection from instance scheduling and token-generation optimisation. Backend queueing and cache state can affect observed latency even when a router selects the same model. The project will measure its own gateway overhead and avoid transferring serving-cluster speedups to the two-machine setting.

**Llumnix** (Sun et al., 2024). *peer-reviewed.* Live request migration and rescheduling will be considered in relation to Serving workloads. Llumnix is an Alibaba multi-instance LLM serving layer that, besides picking a replica, moves running requests with their KV cache between instances. One load metric, "freeness", drives dispatch, migration and auto-scaling.

The relevant boundary is requires serving-engine and instance state. The router will distinguish choosing a model from balancing replicas. Consumer-machine evaluation will not claim to reproduce a datacentre migration system.

**Mooncake** (Qin et al., 2025). *peer-reviewed.* KV-cache-centric disaggregated serving will be considered in relation to Long-context serving workloads. Mooncake is the serving platform behind Moonshot AI's Kimi chatbot. It splits prefill and decode onto separate GPU pools and uses spare cluster CPU, DRAM and SSD as a shared KV-cache store. A global scheduler, "Conductor", sends each request to the prefill node with the lowest predicted first-token time and rejects requests that cannot meet their latency targets.

The relevant boundary is engine and cache infrastructure dependence. This will motivate separate TTFT and completion measurements. Its throughput results will not become expectations for an API gateway.

**RouteBalance** (Da & Kalyvianaki, 2026). *preprint.* Joint quality/cost/load assignment to instances will be considered in relation to Heterogeneous serving cluster. RouteBalance picks, for each request, a concrete model instance (a specific model on a specific GPU) using one score that trades off predicted answer quality, latency and cost. It joins what are usually two separate layers: a model router that ignores load, and a load balancer that ignores quality.

The relevant boundary is preprint; serving-state assumptions. This is adjacent prior art for multi-objective assignment. It prevents a blanket novelty claim while leaving the project's integration and comparisons open to evaluation.

**Sarathi-Serve** (Agrawal et al., 2024b). *peer-reviewed.* Chunked prefill and decode scheduling will be considered in relation to Serving workloads. Sarathi-Serve is a scheduler for one LLM replica that splits long prompts into chunks and packs them into batches next to ongoing decodes, so that no request's token stream pauses. It also gives the clearest definitions in this topic of time to first token, time between tokens and *capacity*.

The relevant boundary is engine-level throughput/latency trade-off. The evaluation will record backend conditions and not attribute an engine scheduling change to the router's predictor.

**DistServe** (Zhong et al., 2024). *peer-reviewed.* Prefill/decode disaggregation for goodput will be considered in relation to Serving and workload traces. DistServe runs the prefill phase (processing the prompt, which sets time to first token, TTFT) and the decoding phase (generating tokens, which sets time per output token, TPOT) on different GPUs. It chooses how many GPUs and which parallelism each phase gets from the application's TTFT and TPOT targets, and measures success as *goodput*.

The relevant boundary is multi-resource deployment assumptions. TTFT and token-generation timing will be reported distinctly. A completion deadline will not be confused with an inter-token service objective.

**Vidur** (Agrawal et al., 2024c). *peer-reviewed.* Profile-based inference simulation will be considered in relation to LLM operator/workload profiles. Vidur predicts how an LLM deployment will perform without running it on GPUs. It profiles each operator once, predicts operator run times, and simulates a replica and a cluster scheduler. Its search tool, Vidur-Search, finds the cheapest configuration that meets latency constraints.

The relevant boundary is simulator fidelity depends on workload and hardware. Replay and predicted latency will be labelled estimates. Measured gateway latency will require a separate live subset on the stated machines.

**PagedAttention** (Kwon et al., 2023). *peer-reviewed.* Paged KV-cache management in vLLM will be considered in relation to Autoregressive serving workloads. vLLM is an LLM serving engine built on PagedAttention, which stores each request's key-value (KV) cache in small fixed-size blocks that need not be contiguous, like pages in an operating system. This almost removes wasted GPU memory, so more requests can run in one batch.

The relevant boundary is serving-engine optimisation rather than model selection. Local serving will use an existing engine where feasible. Memory efficiency will not establish suitability or guarantee that a selected model fits at the desired context length.

**Speculative decoding** (Leviathan et al., 2023). *peer-reviewed.* Draft-and-verify token generation will be considered in relation to Autoregressive generation tasks. Speculative decoding speeds up generation from a large language model without changing its output distribution. A small, fast "approximation" model guesses several next tokens; the large "target" model checks all guesses in one parallel pass and keeps those it would have produced itself.

The relevant boundary is requires a compatible draft/target execution mechanism. This will distinguish inference acceleration from request routing. The study will not assume that opaque hosted APIs expose speculative execution controls.

Taken together, these studies will guide an explicit baseline or design boundary. The proposal will test the selected mechanism under one frozen data and policy contract. It will not combine incompatible metrics or select a favourable operating point from each study as though they described one experiment.
