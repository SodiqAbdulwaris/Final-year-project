### 2.4.6 Reliability and fallback

The reliability review will distinguish engine-state recovery from a fresh model call after an execution error. Gateway fallback will need explicit retry eligibility, remaining-resource checks and partial-delivery rules. The study will evaluate those rules with injected failures rather than infer resilience from an offline quality score.

**SpotServe** (Miao et al., 2024). *peer-reviewed.* Reconfiguration and migration under preemption will be considered in relation to Preemptible GPU traces. A distributed LLM serving system that runs on cheap cloud "spot" GPU instances that the provider can reclaim at any time. When instances disappear or appear, it re-plans how the model is split across GPUs, moves cached state instead of reloading, and keeps partial progress of in-flight requests.

The relevant boundary is engine-level recovery, not gateway model failover. The project will reuse the need for an explicit failure model, without asserting that a fresh call to another model preserves internal execution state.

**DéjàVu** (Strati et al., 2024). *peer-reviewed.* KV-cache streaming and replication will be considered in relation to Pipeline-parallel LLM deployments. A pipeline-parallel LLM serving system whose core is a library that streams the attention key-value (KV) cache between GPUs, CPUs and machines. The same primitive is used for three goals: separating prompt processing from token generation to reduce idle "bubbles", swapping per-microbatch caches to CPU to fit larger batches, and replicating the cache so a failed worker can be repaired without restarting requests.

The relevant boundary is requires access to cache and engine state. Operational fallback will restart only permitted work and will not claim transparent continuation of a partly delivered stream.

**ServerlessLLM** (Fu et al., 2024). *peer-reviewed.* Checkpoint loading, locality and migration will be considered in relation to Distributed inference deployments. A serverless inference system that cuts the "cold start" of loading large model checkpoints onto GPUs. It speeds up loading, schedules a model onto the server with the best checkpoint locality, and, where locality conflicts with a running request, **live-migrates** that inference to another server with little interruption.

The relevant boundary is startup/locality system rather than suitability selection. Cold starts will be recorded in live tests rather than averaged away. Local fallback readiness will be checked independently of model capabilities.

**Metastable failures** (L. Huang et al., 2022). *peer-reviewed.* Incident analysis and reproduced amplification mechanisms will be considered in relation to Public distributed-system incidents. A study of "metastable failures": outages in which a temporary trigger pushes a system into overload and a *sustaining effect* (most often retries) then keeps it down even after the trigger is gone. The authors read hundreds of public incident reports, extend an earlier model, and reproduce several failures in test applications.

The relevant boundary is adjacent distributed-systems evidence. The reliability controller will use bounded attempts and health tracking. The paper will not be cited as direct evidence of this router's fallback success.

Taken together, these studies will guide an explicit baseline or design boundary. The proposal will test the selected mechanism under one frozen data and policy contract. It will not combine incompatible metrics or select a favourable operating point from each study as though they described one experiment.
