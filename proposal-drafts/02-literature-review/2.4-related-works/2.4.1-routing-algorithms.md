### 2.4.1 Routing algorithms

The review will distinguish choosing one model before generation, escalating after an answer and fusing several outputs. These designs will not be treated as interchangeable evidence for the proposed single-request decision policy. The core comparison will ask whether the added predictor features justify their inference and maintenance cost.

**Hybrid LLM** (Ding et al., 2024). *peer-reviewed.* Pre-generation quality-gap routing will be considered in relation to MixInstruct. Easy queries go to the small model, the rest to the large one, and one threshold set at test time trades quality for cost. Each query is answered by exactly one model.

The relevant boundary is binary model choice and quality metric dependence. Its thresholded decision will motivate an inexpensive predictor baseline; its reported savings will not be imported as a project target.

**RouteLLM** (Ong et al., 2025). *peer-reviewed.* Preference-trained routing between stronger and weaker models will be considered in relation to Preference data and held-out benchmarks. RouteLLM trains routers that decide, per query, whether a strong, costly LLM or a weak, cheap one should answer. Routers learn from human preference votes (Chatbot Arena) plus cheap data augmentation. An open-source framework for training, serving and evaluating routers is released.

The relevant boundary is two-model formulation and deployment distribution shift. Preference-derived decisions will inform the baseline design, while the proposed pool will require model-specific estimates and a separate execution policy.

**RouterDC** (S. Chen et al., 2024). *peer-reviewed.* Query/model representations with dual contrastive objectives will be considered in relation to Multi-task model outcomes. Each candidate LLM gets a learnable vector and each query an embedding from a small encoder; the query goes to the LLM with the most similar vector. Two contrastive losses train the router to treat several good LLMs as equally acceptable.

The relevant boundary is evaluated small-model pool; training complexity. The hybrid will borrow the idea of model-specific matching without reproducing dual-contrastive training. An ablation will test whether simple features suffice.

**FrugalGPT** (L. Chen et al., 2024). *peer-reviewed.* Learned response-quality cascade will be considered in relation to Scored API task outputs. The paper outlines three ways to cut LLM API cost (prompt adaptation, LLM approximation, LLM cascade) and builds FrugalGPT, a learned cascade that calls cheap models first and escalates only when an answer looks unreliable.

The relevant boundary is label/distribution dependence; sequential calls. Its escalation mechanism will remain optional. A failed HTTP call will not be treated as the same event as rejection of a completed answer.

**AutoMix** (Aggarwal et al., 2024). *peer-reviewed.* Self-verification and POMDP-based escalation will be considered in relation to Question-answering benchmarks. A small model answers first, then the same model checks its own answer against the context, and the query goes to a larger model only if the check is unconvincing. A POMDP router decides how far to trust the noisy self-check. It needs only black-box API access and few training examples.

The relevant boundary is answer-dependent evidence and sequential inference. This will provide a conceptual comparison with uncertainty-based escalation. The project will not adopt POMDP control in its initial scope.

**Zooter** (K. Lu et al., 2024). *peer-reviewed.* Reward-guided router distillation will be considered in relation to Instruction queries and model rewards. It learns from the scores a reward model gives each candidate's answers on a training set, so at run time only the router and one LLM are used. Tag-based smoothing reduces label noise.

The relevant boundary is dependence on reward supervision. This will motivate future reward-guided work, while current features will be evaluated with a smaller, explicitly scored model pool.

**LLM-Blender** (D. Jiang et al., 2023). *peer-reviewed.* Pairwise response ranking and generative fusion will be considered in relation to Candidate response sets. LLM-Blender queries many open LLMs for every input, ranks their answers with a pairwise model (PairRanker) and merges the top few into a new answer (GenFuser). It is an ensemble, not a router, and later routers use it as the "call everything" reference and reuse its MixInstruct data.

The relevant boundary is multiple candidate generations and fusion overhead. This will clarify why response fusion is excluded initially: it answers a different resource-allocation question from single-candidate dispatch.

**Benchmark-dataset routing** (Shnitzer et al., 2023). *preprint.* Benchmark-supervised routing will be considered using public per-model outcomes. Per-question results from public benchmarks (HELM, MixInstruct) become training data for a router. For each LLM a binary classifier predicts whether it will answer a given input correctly, and the model with the best predicted correctness is recommended for a new task. Only the chosen LLM generates.

The relevant boundary is benchmark-specific labels; preprint evidence. The study will reuse scored records but keep held-out outcomes outside the predictor and retrieval index, rather than treating a benchmark-derived label as universal competence.

Taken together, these studies will guide an explicit baseline or design boundary. The proposal will test the selected mechanism under one frozen data and policy contract. It will not combine incompatible metrics or select a favourable operating point from each study as though they described one experiment.
