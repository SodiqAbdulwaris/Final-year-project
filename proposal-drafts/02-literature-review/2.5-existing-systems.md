## 2.5 Review of Existing Systems

Table 2.2 compares three existing gateway products with the proposed system, using their official documentation accessed on 31 October 2026. This is grey literature and not peer-reviewed evidence of performance. A tick means a documented feature, or a planned feature for the proposal; P means a partial or rule-based form; a question mark means the checked pages did not establish the feature, which is not evidence that it is absent. The ticks for the proposed system are planned, not implemented.

**Table 2.2: Feature comparison from vendor documentation**

| Feature | OpenRouter | LiteLLM | Portkey | Proposed system |
|---|---|---|---|---|
| Per-prompt automatic model selection | ✓ | ✓ | P | ✓ |
| Retries and fallback on execution failure | ✓ | ✓ | ✓ | ✓ |
| Connection to local or self-hosted models | ? | ✓ | P | ✓ |
| Hard budget and privacy limits kept during fallback | ? | ? | ? | ✓ |
| Hybrid task and embedding suitability estimator | ? | ? | ? | ✓ |
| Published ablations and baseline comparisons | ? | ? | ? | ✓ |

OpenRouter documents an Auto Router for per-prompt selection and model and provider fallback (OpenRouter, n.d.). LiteLLM documents an auto router separate from its core load balancer, with retries, cooldowns, timeouts and fallbacks, and routing across deployments (LiteLLM, n.d.). Portkey documents conditional routing policies and prioritised fallback with retry controls (Portkey, n.d.). Product features change, so they will be rechecked before submission.

The project does not claim novelty for offering one endpoint, per-prompt routing or fallback. Its contribution is the specified constrained policy, the comparison against simpler baselines and the separately evaluated recovery.
