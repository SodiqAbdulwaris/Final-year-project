## 2.3 Enabling Technologies and Techniques

The implementation will reuse standard gateway, embedding, classification and serving components where practical. Request validation will define the trust boundary; capability and context metadata will determine eligibility; token accounting and immutable price versions will support budget control. Classification will label task characteristics, and retrieval will supply neighbour-derived features. Suitability prediction will remain distinct from deterministic filtering and health state.

An embedding will represent query similarity; a learned model representation will describe candidate performance. Neither will replace a measured quality label. The k-NN index will be built only from permitted historical records, and any normalisation or calibration will be fitted without access to evaluated test outcomes.

Cost ranking will use a declared expected-cost estimate. A conservative reservation will provide a separate protection against overspending before execution. Predicted latency will be assessed against an explicit deadline rule and then compared with measured timing. Retry cost and uncertain usage will not be erased simply because a provider returned no complete answer.

**MuxServe (Duan et al., 2024; peer-reviewed).** Spatial/temporal multi-model multiplexing addresses llm serving workloads. Its relevant boundary will be resource multiplexing is not prompt-quality routing. The local deployment plan will respect resource contention. A gateway-level choice will not be presented as an implementation of engine multiplexing.

**SGLang (Zheng et al., 2024; peer-reviewed).** Structured LM execution and prefix-cache reuse addresses multi-call lm programs. Its relevant boundary will be runtime optimisations depend on execution control. The project will distinguish protocol capability checks from runtime acceleration. Backend caching will be recorded as an experimental condition.

**AlpaServe (Z. Li et al., 2023; peer-reviewed).** Statistical multiplexing with model parallelism addresses distributed model-serving workloads. Its relevant boundary will be cluster placement differs from API selection. The proposal will avoid claiming distributed GPU scheduling. Host roles will be chosen for a feasible pilot, not derived from cluster-scale results.

**S-LoRA (Sheng et al., 2024; peer-reviewed).** Paging and batching multiple adapters addresses lora serving workloads. Its relevant boundary will be adapters share a base model. This will define another boundary: adapter multiplexing will not establish quality-aware selection across independent hosted and local models.

The project will not implement these serving algorithms. It will use vLLM or Ollama as an execution backend where hardware fit permits and will keep the backend configuration fixed when comparing routing policies. Differences in quantisation, context limits, caching and warm-up will be recorded to avoid attributing them to the selector. Redis/Prometheus, direct GPU/queue telemetry and managed-session mechanisms will remain unresolved earlier proposals.
