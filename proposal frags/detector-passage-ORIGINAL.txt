This chapter explains the problem the proposed LLM request-routing gateway will address. It sets out the aim, objectives and research questions, followed by the proposed methods, scope, limitations and contributions. A software application can access a large language model (LLM) through a hosted API or a locally operated deployment. The available deployments differ in their capabilities, charges, response times and availability; they can also perform differently on the same task. An application that sends every request to one model has a simple integration, but cannot adjust its choice for individual requests. FrugalGPT, Hybrid LLM and RouteLLM show that selecting among models can change the balance between cost and response quality (Chen et al., 2023; Ding et al., 2024; Ong et al., 2025). Those results motivate this study, although they do not show that the proposed gateway will outperform simpler approaches. The proposed router will sit between client applications and model deployments. Besides estimating which model may suit a request, it must validate that request, apply policies, select an eligible endpoint and report failures. Its operation must be observable. The project will therefore specify, build, deploy and test the gateway with attention to performance efficiency, reliability, security, compatibility and maintainability. This work concerns the choice of a deployment for each request. It does not seek to replace the inference scheduler inside a model server. PagedAttention addresses a different part of the problem: memory management within model-serving infrastructure (Kwon et al., 2023). The gateway may use hosted and local endpoints where the necessary resources and permissions are available. The selection approach will combine two sources of evidence: a classification of the task and embedding-derived comparisons with requests that have already been evaluated. Together, they will inform estimates of each model’s suitability. The gateway will first rule out deployments that fail declared capability, budget, privacy or operational constraints. It will then compare the eligible deployments using estimated quality, cost and latency. Health monitoring and bounded fallback will handle failures after selection. Tests will examine whether each learned component improves the decision. Existing benchmark data can support repeatable comparisons. RouterBench, for example, was designed to evaluate routing strategies (Hu et al., 2024). Replaying stored outputs cannot, however, establish actual network latency, provider availability or behaviour during injected failures. For that reason, offline experiments will be accompanied by integration tests and a limited live or controlled deployment evaluation. The project aims to produce a documented, deployable gateway and evidence of the benefits and overhead of the hybrid selection strategy. The growing use of Large Language Models (LLMs) has introduced challenges in managing response quality, cost, and latency. Many applications rely on a fixed model for all requests, regardless of their complexity. This can increase costs for simple tasks or reduce response quality for more complex ones. Research by Chen et al. (2023) and Ding et al. (2024) has demonstrated that selecting models based on request requirements can improve efficiency and reduce operational costs. The quality comparison will use an evaluation margin and scoring protocol fixed before the held-out results are examined. Any cost or latency reductions will be measured. Chapter Three will set out the hypotheses, metrics, sample selection and uncertainty analysis. The proposed LLM Router System will be developed using the Scrum framework, an Agile software development approach that emphasizes iterative development, teamwork, flexibility, and continuous improvement. Scrum was selected because it allows the project to be divided into smaller, manageable tasks and developed incrementally, making it easier to monitor progress, identify challenges, and incorporate improvements throughout the development process. The development process will be organized into short iterations known as Sprints, with each Sprint focusing on specific features of the system. These features will include model integration, intelligent request routing, performance evaluation, cost and latency monitoring, and dashboard development. At the end of each Sprint, the team will review the completed work, test the implemented features, and gather feedback to guide subsequent development. The project team will maintain a Product Backlog containing the system requirements, features, and tasks to be implemented. During Sprint Planning, tasks will be prioritized and assigned to team members based on the project's objectives. Regular team meetings will be conducted to discuss progress, address challenges, and ensure effective collaboration. Sprint Reviews and Retrospectives will also be used to evaluate completed work and improve the development process.
