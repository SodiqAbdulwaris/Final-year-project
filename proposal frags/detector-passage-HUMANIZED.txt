This chapter will highlight the problem that the proposed LLM request-routing gateway is intended to solve. This chapter outlines the aim, objectives and research questions for the study before detailing the proposed methodology, scope, limitations and contributions. For a software application, a large language model (LLM) can be accessed via a hosted API or a locally run deployment. The characteristics of the deployments vary: their capabilities, fees, latency and availability. The performance of the deployments might differ when handling the same task. Integrating the application in the case where all requests are directed to a specific model is straightforward, but there is no possibility to change the model on a per request basis. FrugalGPT, Hybrid LLM, and RouteLLM have demonstrated that model selection can affect the trade-off between cost and response quality (Chen et al., 2023; Ding et al., 2024; Ong et al., 2025). While the results of these studies are the motivation for this study, they do not provide evidence that the proposed gateway will be more effective than simpler solutions. The proposed router will operate as the intermediary between the client applications and the model deployments. Aside from estimating which model might fit a request, it is responsible for validating it, policy enforcement, finding a suitable endpoint and signaling failures. The router's activities must be observable. For this reason, the project will define, develop, deploy and test the router considering the performance efficiency, reliability, security, compatibility and maintainability. This work is about which deployment to use for a given request. It is not aiming to substitute the model server inference scheduler. PagedAttention looks at a different problem, which is the memory management problem inside model serving infrastructure (Kwon et al., 2023). The gateway can make use of hosted endpoints and local endpoints if the resources and permissions are there. The selection approach will combine two sources of evidence: a classification of the task and embedding-derived comparisons with requests that have already been evaluated. Together, they will inform estimates of each model’s suitability. The gateway will first rule out deployments that fail declared capability, budget, privacy or operational constraints. It will then compare the eligible deployments using estimated quality, cost and latency. Health monitoring and bounded fallback will handle failures after selection. Tests will examine whether each learned component improves the decision. With existing benchmarks there is potential to provide repeatable comparisons. For instance the RouterBench is intended to assess the routing strategies (Hu et al., 2024). However, it is not possible to retrieve real network latency, availability of provider or behaviour in the case of injecting failures by replaying stored outputs. Therefore, integration tests and a small-scale evaluation in live (or controlled) deployment will be performed alongside the offline experiments. The goal is to have a documentable gateway that can be deployed as well as to showcase gains and overhead of the hybrid selection strategy. With the popularity of Large Language Models (LLMs), issues arise for controlling response quality, cost, and latency. Most of the time, a single model serves all requests without taking into account complexity. This means that it could be expensive when simple requests are made, or the response quality could decrease when complex requests are made. In recent works, Chen et al. (2023) and Ding et al. (2024) have shown how a model choice corresponding to request requirements can increase efficiency and lower operational cost. An evaluation margin and scoring method for quality will be pre-defined and used for the quality comparison. All cost and latency savings will be measured. The hypotheses, metrics, sample, uncertainty analysis will be defined in Chapter Three. The Scrum framework will be used for the development of the proposed LLM Router System. Scrum is an Agile software development methodology focused on iterative development, collaboration, adaptability, and continuous enhancement. Scrum has been chosen because it enables breaking down the project into smaller, more manageable tasks and developing it iteratively. This facilitates tracking progress, identifying difficulties, and making improvements along the way. The development of the system will be divided into small iterations called Sprints, which will concentrate on certain parts of the system. These features may include model integration, intelligent request routing, system performance assessment, cost and latency tracking, and developing dashboards. The deliverables of each Sprint will be examined, tested with the features implemented, and evaluated with feedback. This feedback will inform further development. They will keep a Product Backlog which will have all the requirements, features and tasks that needs to be done for the system. During Sprint Planning, the tasks will be prioritized and assigned to members based on the goals of the project. Periodic team meetings will be held to discuss progress, problems and team collaboration. Sprint Reviews and Retrospectives will be held to review what has been done and improve the development process.
